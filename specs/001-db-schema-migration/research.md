# Research: Petstore Database Schema Migration

All items below were decidable from the existing OpenAPI contract plus conventions already locked in `CLAUDE.md` / `packages/api/CLAUDE.md`. No `[NEEDS CLARIFICATION]` markers remain from the spec, so this file documents the concrete technical decisions the plan builds on rather than resolving open unknowns.

## 1. Changelog format

- **Decision**: Liquibase *formatted SQL* changelogs (`.sql` files with `--liquibase formatted sql` + `--changeset` headers), included from a single `db.changelog-master.yaml`.
- **Rationale**: Already mandated in `packages/api/CLAUDE.md` — plain SQL is what the team reads/writes day to day; YAML/XML changeset types are reserved for cases formatted SQL can't express (none here).
- **Alternatives considered**: Liquibase native XML changesets (more verbose, no benefit for straight DDL); Liquibase native YAML changesets (same); a Node-based migration runner such as `node-pg-migrate` (rejected — the project has already standardized on Liquibase specifically to keep schema history tool-agnostic).

## 2. Primary key strategy

- **Decision**: `BIGINT GENERATED BY DEFAULT AS IDENTITY` for every table's `id` column.
- **Rationale**: Every entity's `id` in the OpenAPI contract is `type: integer, format: int64` — `BIGINT` is the exact match. Identity columns are the modern, SQL-standard replacement for `SERIAL` in PostgreSQL.
- **Alternatives considered**: UUID surrogate keys (rejected — spec's Assumptions explicitly reuse the contract's numeric `id`); legacy `SERIAL` (rejected — identity columns are the current best practice and behave better with `GENERATED BY DEFAULT` allowing explicit inserts when needed, e.g. fixtures/tests).

## 3. Many-to-many Pet↔Tag

- **Decision**: Join table `pet_tags(pet_id, tag_id)` with a composite primary key, both columns foreign keys with `ON DELETE CASCADE` (the association row has no meaning once either side is gone, but the `tag`/`pet` rows themselves are never cascaded away by this relationship).
- **Rationale**: Standard normalized many-to-many; satisfies FR-002 and keeps Tag rows reusable/unique (FR-012) instead of duplicating tag strings per pet.
- **Alternatives considered**: `text[]` tags column directly on `pets` (rejected — can't enforce FR-012 uniqueness or reuse tags across pets without application-level bookkeeping).

## 4. Pet photo URLs

- **Decision**: Child table `pet_photo_urls(id, pet_id, url, position)`, `position` preserving contract order, `ON DELETE CASCADE` from `pets`.
- **Rationale**: FR-003 requires an *ordered* collection of zero or more URLs per pet. A child table with an explicit `position` column models order and cardinality exactly, and keeps every "collection on an entity" case (tags, photo URLs) in the same relational shape.
- **Alternatives considered**: PostgreSQL `text[]` array column (rejected — no explicit ordering guarantee across all access patterns, and awkward to express in a type-safe way through Kysely without array-specific escape hatches); JSON column (rejected — gives up column-level constraints for no benefit here).

## 5. Status enforcement

- **Decision**: Plain `VARCHAR` status columns with a `CHECK` constraint against the contract's fixed value list (`available|pending|sold` for pets, `placed|approved|delivered` for orders).
- **Rationale**: Satisfies FR-006/FR-007 and SC-004. `CHECK` constraints are trivial to extend later (`ALTER TABLE ... DROP CONSTRAINT ... ADD CONSTRAINT ...` in one changeset) if the contract ever adds a status value.
- **Alternatives considered**: Native PostgreSQL `CREATE TYPE ... AS ENUM` (rejected — altering enum values later is more awkward than altering a `CHECK` constraint, and formatted-SQL Liquibase changesets are simplest when each changeset is a self-contained, easily-reviewed statement).

## 6. Foreign key delete behavior

- **Decision**:
  - `store_orders.pet_id → pets.id`: `ON DELETE RESTRICT` (blocks deleting a Pet with existing Orders — FR-011 / Edge Cases).
  - `pets.category_id → categories.id`: `ON DELETE SET NULL` (Category association is optional per FR-004; deleting a Category detaches Pets rather than deleting them).
  - `pet_tags.*` and `pet_photo_urls.pet_id`: `ON DELETE CASCADE` from `pets` (these rows have no independent meaning without their owning Pet).
- **Rationale**: Directly implements the Edge Cases and FR-004/FR-011 from the spec.
- **Alternatives considered**: Cascading Pet deletes onto Orders (rejected — would silently destroy order history); hard-blocking Category/Tag deletion entirely (rejected — reference data should remain deletable; only the Pet↔Order link is business-critical enough to block).

## 7. Uniqueness and audit columns

- **Decision**: `UNIQUE` constraint on `categories.name`, `tags.name`, and `users.username` (FR-008, FR-012). Every table gets `created_at TIMESTAMPTZ NOT NULL DEFAULT now()` and `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`, with a shared trigger function that sets `updated_at = now()` on every `UPDATE` so application code never has to remember to set it.
- **Rationale**: Directly implements FR-008/FR-012 and the spec's audit-column Assumption; a single reusable trigger function keeps `updated_at` correct without relying on every future repository method to set it by hand.
- **Alternatives considered**: Leaving `updated_at` maintenance to application code (rejected — easy to forget in one repository method and silently get a stale value).

## 8. Table naming

- **Decision**: All tables plural, snake_case: `pets`, `categories`, `tags`, `pet_tags`, `pet_photo_urls`, `store_orders`, `users`.
- **Rationale**: `order` is a reserved SQL keyword and unsafe as a bare identifier, so the OpenAPI "store" tag's `Order` entity becomes `store_orders`, consistent with the module name. Making every table plural (including the join/child tables, which are already natural plurals) keeps one consistent rule instead of mixing singular and plural conventions.
- **Alternatives considered**: Singular table names (`pet`, `category`, ...) with `"order"` quoted everywhere it's used (rejected — quoting a reserved word correctly in every query is an easy mistake to make; not worth it to save one table rename).

## 9. Migration file naming

- **Decision**: `NNNN-verb-object.sql`, four-digit zero-padded sequence starting at `0001`, one changeset per table, all referenced in order from `packages/api/migrations/db.changelog-master.yaml`.
- **Rationale**: Matches the convention already documented in `packages/api/CLAUDE.md`; keeps each changeset small and independently reviewable.
- **Alternatives considered**: Timestamp-prefixed filenames (common Rails/Liquibase convention) — rejected only because the project's own CLAUDE.md had already settled on sequential numbering before this feature.

## 10. Entity-relationship diagram

- **Decision**: Hand-authored Mermaid `erDiagram` in `packages/api/architecture/erd.md`, kept in sync manually with the migration (one PR touching the schema should touch both).
- **Rationale**: Satisfies FR-010/SC-003/SC-005 with zero new tooling for a 7-table schema.
- **Alternatives considered**: Auto-generating the diagram from the live DB via a schema-introspection tool (e.g. `tbls`) — rejected as unnecessary tooling overhead at this scale; worth revisiting if the schema grows substantially.
